# UniTn RAG Pipeline — Development Notes

Reference notes on the design decisions, experiments, and findings behind a retrieval-augmented chatbot built over a web-scraped University of Trento document corpus. Scoped to the work done from the point the pipeline first reached a documented, evaluated baseline onward. Organized by topic rather than by session, for reuse in thesis writing. Each section covers what was done, the reasoning behind it, and — where relevant — what was tried and did not work.

## 1. Baseline system, as first fully documented

By the time of the first full documented checkpoint, the pipeline already had the following in place, and this section describes it as inherited groundwork for everything that follows.

**Ingestion and indexing.** Each crawled document is stored as one record in a rich schema (URL, fetch timestamp, HTTP status, content type, etag/last-modified for change detection, a resolved effective year, academic year, language and language-source, document type, department, extractor used, title, full text, a duplicate-of pointer, and a changed flag). An OCR pass recovers text from image-only PDFs that would otherwise contribute nothing (verified concretely on at least one travel-regulation PDF that had zero extractable characters before OCR). A delta-crawl mechanism uses etag/last-modified headers to re-crawl only changed pages rather than the whole site. Documents are language-filtered to Italian/English and very short documents (under 150 characters) are dropped before indexing.

Two indices were built and compared over the same corpus: one using fixed-size chunking throughout, and one using a hybrid scheme that additionally applies semantic (embedding-boundary-aware) splitting specifically to longer documents. Building or rebuilding either of these indices — reprocessing the corpus, re-chunking, and re-embedding every chunk — is the expensive, infrequent operation in this pipeline; it is distinguished throughout these notes from the much cheaper *retrieval-time re-scoring* changes described in later sections, most of which required no reindexing at all because they operate on chunks that are already embedded and stored.

**Chunking, including header enrichment.** The primary chunking scheme splits documents into 512-token windows with 100-token overlap. A specific enrichment step — *header injection* — prepends a short block (title, source URL, language, and resolved academic year) directly into each chunk's text before it is embedded, so that this metadata is actually present in the vector the retriever matches against, rather than sitting only in a separate, unsearched metadata field. This matters because a question naming a course or department by name benefits from that name being embedded alongside the chunk's content, not just stored alongside it. For long documents (roughly 80% of the corpus's total text, and the large majority of it PDFs without usable heading structure), the alternative semantic-chunking scheme was applied as a hybrid on top of the same header-injection step, to test whether respecting semantic boundaries in long, unstructured PDFs would keep more of a fact's supporting context together with it.

**Retrieval (as first built).** Dense retrieval uses BGE-M3 embeddings, chosen specifically over an English-only alternative because the corpus is substantially Italian-language. A fixed number of raw candidate chunks is retrieved per query, then re-scored in a post-retrieval step: a recency multiplier favoring more recent documents, a small tie-break favoring the chunk whose language matches the query's language, and a URL-based affinity boost rewarding candidates whose host or path terms overlap with terms extracted from the question. Candidates are deduplicated so that only one chunk per document group (collapsing a document's IT/EN translation pair to a single slot) and one chunk per document reach the generation step, up to a fixed maximum number of distinct source pages.

**Generation and safety (as first built).** The system prompt isolates end-user input inside a dedicated tag with an explicit instruction never to treat its contents as instructions (the primary prompt-injection defense). Generation is constrained to the retrieved context only, with an explicit instruction to read the entire context before concluding an answer is absent (since a relevant fact is often in a table row or list item rather than a full sentence), a fixed exact-string refusal phrase chosen specifically so it can be detected programmatically during evaluation, a per-claim citation requirement, and a same-language-as-the-question rule reinforced by naming the target language explicitly in the prompt (a generic instruction to "answer in the question's language" was found not to be reliably followed on its own when most of the retrieved context happened to be in the other language). A separate, cheap upstream classifier gates whether a query is in-scope before retrieval even runs.

**Evaluation harness.** A 41-question, deliberately adversarial evaluation set is scored on retrieval (hit@k: is a correct source among the top *k* retrieved) and, separately and less consistently over the project's history, on generation correctness by manual grading. Because the retrieval pipeline's own deduplication collapses a document's bilingual pair to a single slot, a single "target URL" per question was found to produce structural false negatives — a retrieval that is correct via a document's other-language sibling would score as a miss — so the scoring function was extended earlier in the project to accept a list of acceptable URLs per question rather than one, populated partly by an automated bilingual-pairing method and partly by URLs discovered as valid alternative sources during manual grading. A small number of questions (where the correct fact is repeated identically across dozens of unrelated documents with no single canonical source) are explicitly excluded from the retrieval metric's denominator, since no retriever can be fairly judged on singling out one specific instance of a universally repeated fact, while remaining scored on generation correctness.

## 2. First documented evaluation round: two bugs found by manual grading, and a chunking ablation

**The chunking ablation was a clean negative result.** Across two independent evaluation rounds, the fixed-chunking and hybrid-semantic-chunking indices never separated by more than a single question out of forty-one — including on the specific long-PDF cases the semantic scheme was hypothesized to help, where it rescued none of the persistent failures and in one case made a result worse. A second round reversed the (already noise-level) direction of the difference. This was treated as sufficient evidence that the added complexity and cost of semantic chunking was not justified for this corpus, and the simpler fixed-chunking index was kept going forward. Properly resolving the question with statistical confidence would need several runs per arm to establish a variance band, which was judged not worth the cost for what was, at best, a one-question effect.

**Bug: an inverted recency ranking.** The recency-scoring multiplier was intended to favor more current documents, using a resolved "effective year" per document. But for documents where no year could be reliably parsed from the document's own content, the multiplier fell back to treating the *crawl or upload* date as if it were the document's real date. Because a large share of the corpus had been crawled or re-crawled recently regardless of the underlying document's actual age, this systematically rewarded exactly the documents it should have penalized: a concrete case found during grading showed a 2002-era student guide, re-uploaded and re-crawled recently, scoring a full, unpenalized freshness multiplier while the genuinely current guide for the same program scored roughly half that. The fix built a small evidence hierarchy for resolving a document's year — preferring what the document's own filename or text states about its edition over what the crawl date alone implies, and only falling back to the crawl-derived year when nothing better is available. This required no reindexing: it operates entirely as a scoring-time function over already-embedded chunks.

**Bug: retrieved chunks were silently truncated before the LLM saw them.** A character-length cap applied to retrieved chunk text at generation time was set below the actual size of the chunks it was applied to (chunks are 512 *tokens*, which is on the order of 1,500–2,500 characters of Italian or English text once the header-injection block is added, while the cap was roughly half that). This meant the tail of nearly every retrieved chunk was being discarded *after* retrieval had already correctly found the right passage — so a question could retrieve exactly the right document and chunk and still fail, simply because the fact it needed sat past the cut. Raising the cap to match the actual chunk size was one of the two highest-impact fixes found in this project, and it reproduced consistently on both chunking arms being compared in the same round, which was itself useful confirmation that it was a real, chunking-independent effect rather than noise in a single arm. No reindexing was required for this fix either — it is applied to text already stored, not to how the corpus was embedded.

**Addition: URL-based affinity scoring for department/course matching.** A recurring failure pattern was two different departments or courses publishing near-identical documents (an academic calendar, a course guide) in nearly the same wording, differing only in the specific values that matter to the question — with no year-based signal able to distinguish them, since both documents could be equally current. A URL-based affinity mechanism was added to boost candidates whose URL host or path terms overlap with terms extracted from the question, using a stoplist to exclude generic filler words and a small alias map connecting an English discipline name to its Italian departmental subdomain.

**Net effect of this round.** Manually grading all 41 questions before and after these fixes moved the score from 56% to 60–62% correct, depending on which chunking arm was measured (the two arms remained within noise of each other throughout, consistent with the ablation finding above). At this point a catalogue of known, still-open failure modes was recorded for future work, including: near-identical sibling pages across departments only partly addressed by the new affinity mechanism; cross-language cases where a fact exists in only one of the corpus's two languages; a tendency to enumerate every retrieved candidate value rather than commit to one when several similar records were retrieved together; at least one case of confident, fluent, fully-cited wrongness (a real but incorrect person named as a course coordinator, with a real but incorrect phone number and email attached); at least one case where the underlying university documentation appeared to genuinely contradict itself across two of its own pages; and obfuscated contact information (deliberately mangled on the source page to deter scraping) leaking through into generated answers in its unusable, obfuscated form rather than being normalized.

## 3. Corpus and index rebuild (v2 → v3)

At some point after the checkpoint described above, the corpus and its index were rebuilt under a new version identifier (a new corpus file and a correspondingly new index directory replaced the pair of indices — one fixed-chunked, one hybrid-semantic-chunked — used in the round above). This is a materially different kind of change from everything else described in these notes: it is a full reprocessing and re-embedding of the corpus, not a retrieval-time scoring adjustment. Note for completeness: the specific content differences introduced by this rebuild (what was added, removed, or re-crawled) are not captured in the project documentation reviewed for these notes — only that the version change happened, evidenced by every subsequent evaluation run's configuration pointing at the new corpus and index rather than the old pair. This is flagged here deliberately as a documentation gap rather than glossed over: a corpus/index rebuild is exactly the kind of change whose specifics (row counts, what was added or dropped, whether chunking parameters changed) should be recorded at the time it happens, precisely because — unlike a scoring-function change — it cannot be trivially re-derived or diffed after the fact without re-running the ingestion pipeline against both corpus versions.

The general point worth drawing out for methodology purposes: the large majority of fixes described in these notes (recency scoring, URL affinity, chunk-length limits, the reranking and crowding fixes described next) are retrieval- or scoring-time changes that require no reindexing and can be iterated on quickly, in contrast to a genuine corpus/index rebuild, which is comparatively expensive and, in this project, was not something the day-to-day experimentation loop touched.

## 4. Reranking: from a proposed late-interaction (MaxSim) approach to a shipped cross-encoder

### 4.1 The originally proposed mechanism: late-interaction rescoring with MaxSim

Before any reranking mechanism was implemented, the first proposal considered was to rescore an already-retrieved, deep candidate pool using late-interaction (ColBERT-style) scoring, computed from BGE-M3's own secondary multi-vector output — the same embedding model already used for dense retrieval, but using an output that ordinary dense retrieval discards. The scoring function considered (MaxSim) computes, for a query with token embeddings $E(q)$ and a document with token embeddings $E(d)$:

$$s(q,d) = \sum_{i \in q} \max_{j \in d} E_i(q) \cdot E_j(d)$$

That is: for every query token, take its highest similarity to any single document token, and sum those maxima across all query tokens. This is a token-level, "did any part of the document strongly match any part of the query" score, in contrast to a single pooled dense-embedding cosine similarity, which compresses the entire query and the entire document into one vector each before comparing.

The appeal of this specific proposal was that it required no new model and no new index: BGE-M3 can be loaded with multi-vector output enabled (`return_colbert_vecs=True` in the `FlagEmbedding` library's `BGEM3FlagModel`), producing exactly the per-token vectors MaxSim needs, from the same forward pass already being run for dense retrieval. The plan was to insert this scoring step between the existing dense-retrieval call and the existing post-retrieval re-scoring step, with two implementation cautions noted in advance: scores need to be normalized into a positive range before being multiplied by the recency and affinity multipliers used downstream, since those multipliers are applied by multiplication and a negative similarity score multiplied by a sub-1.0 penalty becomes *larger*, silently inverting the intended ranking; and the candidate pool retrieved before this rescoring step needs to be substantially deeper than what plain dense retrieval needs on its own, since a rescoring step is only useful if the correct document is actually somewhere in the pool it is given to rescore.

### 4.2 What actually shipped: a cross-encoder reranker

The mechanism that was ultimately implemented and deployed was a standard cross-encoder reranker (a separately trained model, distinct from BGE-M3, that takes the query and a candidate document together as joint input and outputs a single relevance score), applied over a deep per-language candidate pool, ahead of the existing post-retrieval scoring step. This is conceptually related to the MaxSim proposal in §4.1 — both are *rescoring* mechanisms applied to an already-retrieved candidate pool, as opposed to *first-stage* retrieval mechanisms that determine which documents enter the pool in the first place — but they are not the same mechanism. A cross-encoder jointly attends over the full query and document text and produces one discriminative relevance score per pair; MaxSim aggregates independently-computed per-token similarities without any joint attention between query and document. The cross-encoder was the one actually built and measured; the MaxSim/BGE-M3-colbert-head approach remained a documented proposal that was not implemented, once the cross-encoder was shown to work well enough that the additional implementation risk (particularly the score-normalization caution above) was not judged worth incurring for a second, unvalidated rescoring approach.

**A necessary side effect once reranking was active:** several scoring mechanisms that had previously measured as beneficial on top of plain dense retrieval — the query-language tie-break, the URL affinity boost (§2), and the recency multiplier — were re-measured with reranking active and found to be net-negative in that combination, and were disabled. The reranker's own joint scoring was already capturing much of what those heuristics had been approximating on top of a weaker first-stage ranking; stacking a heuristic multiplier on an already-good cross-encoder ranking sometimes moved a correctly-ranked candidate in the wrong direction. This is a general caution for combining multiple re-scoring mechanisms: validating one heuristic in isolation does not guarantee it remains beneficial once a stronger, later-added mechanism is introduced alongside it — each combination needs to be re-measured, not assumed.

### 4.3 A new crowding failure introduced by reranking, and the fix

Once reranking was active with an appropriately deep candidate pool, a new variant of the department/course crowding problem from §2 appeared: for a sufficiently broad question, the reranker's top-ranked results would sometimes be filled almost entirely by near-duplicate documents from the *same* family — several edition-years of the same regulation, or a course-catalogue page together with several of its own exam-module sub-pages — crowding out a genuinely different, correct document that would otherwise have ranked well.

The fix introduced a document-family grouping distinct from the existing bilingual-pair grouping: documents were grouped as structural siblings when they are successive editions of the same regulation (identified by a trailing edition year in the filename) or when they are a course-catalogue page together with its own sub-pages (grouped by shared course and academic-year identifiers in the URL path). A cap was then applied to how many of the final selected results may belong to the same family, backfilling from the excluded candidates so the total number of results returned never drops below the intended count purely because of the cap. A mild recency-scoring weight was reintroduced specifically to help break ties *between* editions of the same family once the family cap forces a choice among them — reintroducing, in a narrower and more targeted form, a mechanism that had been disabled in §4.2.

### 4.4 A second-order regression from that fix, and its correction

Reintroducing recency scoring to break family-cap ties produced its own further regression, worth recording as a case study in how a fix can cascade. With recency scoring active again, documents with no confidently resolvable year (which should mean "no evidence about staleness either way") were scoring *worse* than documents that merely stated the current or an upcoming academic year somewhere in their filename — including documents entirely unrelated to the question, such as an admissions-cycle announcement or an unrelated department's calendar. The result was that several previously-correct, genuinely relevant but undated documents began losing to freshly-dated-but-irrelevant ones purely on this freshness signal. The correction changed what an unresolvable year defaults to in the scoring function, so that "unknown" ties with "confidently current" rather than scoring below it — meaning a document can no longer manufacture a ranking advantage purely by stating a current year if a competing document's actual relevance is otherwise equal or better. A full evaluation re-run confirmed this resolved the regression with no new losses relative to the pre-regression baseline, and in fact produced the strongest retrieval result measured at any point in the project.

**The general point this sequence illustrates:** three fixes were needed in succession to reach a stable state (reranking → family cap → recency-default correction), each one fixing a problem the previous fix had introduced. Retrieval tuning in a system with several interacting re-scoring mechanisms cannot be validated one mechanism at a time in isolation — every change needs a full-scale re-evaluation that specifically checks for regressions on previously-passing questions, not only a check that the targeted questions improved.

### 4.5 Query translation, including a silent-failure incident worth recording

Separately from reranking, a query-translation mechanism was implemented to address genuinely cross-lingual failures — an Italian-language question whose correct source exists only in English, or vice versa — by translating the query into the corpus's other language (via the same LLM already in the pipeline), retrieving for both the original and translated query, and merging the candidate sets before downstream scoring.

**A configuration flag being enabled does not guarantee the corresponding mechanism executed.** An entire evaluation run was later found to have silently fallen back to monolingual retrieval for every single question, despite translation being enabled in configuration and correctly wired in code, traced to the translation call failing open (degrading silently rather than raising an error) against what was most likely a transient backend availability issue. This was only caught because a cache file the translation mechanism is expected to populate on every successful call was conspicuously empty after the run completed — nothing else about the run's output made the failure visible. The general lesson: a fail-open design is often reasonable on its own (it avoids blocking a user over an infrastructure hiccup), but it makes a code path's total, silent failure indistinguishable from that path simply not being needed, unless something separately and explicitly records whether it actually ran successfully. Once confirmed genuinely active (verified by the cache file populating correctly across all questions in a subsequent run), translation was confirmed via a targeted, step-by-step probe to work exactly as intended on a specific case it was meant to fix — pulling a document into the retrieved candidate pool that the untranslated query alone left far outside it.

### 4.6 Candidate pool depth

A diagnostic script was built to directly measure the true rank of each known-correct document within a much wider raw candidate pool than what a first read of the primary retrieval-depth configuration value suggested was in use — this was necessary because that shallower value only governs candidate depth when reranking is *disabled*, and reranking being active means a separate, much deeper configuration value is actually the one in effect. The diagnostic itself needed two bugs fixed before it produced trustworthy numbers: it initially overrode the wrong configuration field (the one that has no effect when reranking is active), and it did not sort merged bilingual-query candidate lists by score before computing rank, producing meaningless rank numbers for any translation-boosted case. Once corrected, the diagnostic confirmed that the production system already retrieves a substantially deep candidate pool per query language — meaning the premise behind "is the candidate pool too shallow" was false from the outset for the great majority of remaining failures, which were ranking-order problems within an already-generous pool rather than absence-from-pool problems. This mattered because it ruled out an entire category of possible next steps (anything aimed at widening recall) as not addressing the actual failures observed.

### 4.7 Alternatives considered and explicitly not pursued

**Hybrid sparse (lexical) retrieval**, using the same embedding model's secondary sparse-weighting output alongside dense retrieval, was scoped as a promising fix for a different residual failure class — exact-match lookups (a named person, a phone number, a precise multi-word regulatory term) that dense semantic similarity handles unreliably — but was not implemented. It was sequenced behind the mechanisms above on the reasoning that it specifically complements cross-lingual retrieval once that is confirmed reliable, and its major limitation (no vocabulary expansion across languages) means it would not help the cross-lingual failure class at all on its own.

**A full first-stage, token-level multi-vector retrieval architecture (the ColBERTv2 design)**, which would use MaxSim-style scoring as the primary retrieval mechanism over the entire corpus rather than as a rescoring step over an already-narrow pool, was considered in depth and explicitly not adopted. This requires specialized infrastructure — residual vector compression and a multi-stage pruning cascade (PLAID) — specifically to make token-level scoring computationally tractable over corpora at a scale (tens of millions of documents and beyond) that this project's corpus does not approach. Two points were drawn out clearly in reaching this decision: first, this first-stage multi-vector architecture is a genuinely different mechanism from either the MaxSim rescoring idea in §4.1 or the cross-encoder that shipped in §4.2, despite the superficial naming overlap — a rescoring step improves ranking within a pool another mechanism already generated, while this architecture would replace how the pool itself is generated; second, and more decisively, the diagnostic work in §4.6 had already shown that the project's actual retrieval failures were consistently ranking-order problems solvable by rescoring an existing, adequately deep pool, not recall-ceiling problems where the correct document never entered any reasonably-sized pool at all — which is specifically the failure class this heavier architecture exists to solve. Adopting it here would mean several weeks of engineering effort and a second retrieval index to maintain, to address a problem this corpus does not exhibit at its actual scale.

**A subset evaluation index built only from evaluation-target documents** (to speed up experimentation) was considered and rejected: it would make retrieval metrics incomparable across index versions, and — more importantly — it would remove exactly the near-duplicate, wrong-department "distractor" documents that create the crowding failures this work spent most of its effort characterizing and fixing. A representative evaluation has to include the noise the production system will actually face.

## 5. Generation-side findings

### 5.1 Manual answer grading as a bug-finding method, not just a scoring method

For a substantial stretch of this project, only retrieval quality (hit@k) was measured across multiple full evaluation runs; whether the generated answer was actually correct was left ungraded. When a full manual grading pass was eventually done — reading every generated answer against its gold answer, and specifically checking whether the *cited* source actually supports the claim made, rather than only checking whether the citation matches a pre-written expected URL — it surfaced findings no retrieval metric could have caught on its own:

- A citation-extraction bug (a regular expression intended to parse bracketed citation markers like `[2]` out of generated answers only matched a single number per bracket, silently dropping every multi-source citation such as `[2, 6]` or `[1, 3, 6, 8]`) was found this way, by noticing that answers visibly containing bracketed citations were being recorded as citing nothing. This had been silently undercounting real citation behavior across every prior analysis of "how often does the model cite its sources" in the project. It was fixed with a corrected pattern that captures a comma-separated run of numbers inside one bracket, with unit tests added covering single citations, multi-number citations with and without spacing, multiple separate bracket citations, and the empty/no-citation case.
- Two answers that initially looked like the most severe class of failure — a confident, specifically wrong claim, fully cited — were reclassified once the actual cited source page was checked directly. In one case, the source page genuinely contained a typo the generated answer faithfully reproduced (a source data-quality issue, not a generation fault). In another, the source genuinely listed the numbers the model gave, under a broader departmental heading, for a question that was itself ambiguous between "a specific person's line" and "the department's general line" — a defensible reading of an ambiguous question, not a fabrication. Zero confirmed hallucinations, in the specific sense of a citation that does not actually support its claim, were found across the full 41-question pass. This is presented as a methodological point worth stating explicitly: a generation failure should be diagnosed by checking whether the citation supports the claim, not by checking whether it matches a human-authored gold answer's assumption about which source is canonical — the eval set's author cannot exhaustively know every equally valid alternative source in a corpus of tens of thousands of documents.

### 5.2 Retrieval fixes do not automatically fix generation

Re-checking the specific answers affected by the crowding regression described in §4.3–§4.4, once the corrected retrieval was confirmed to surface the right document again, produced a mixed result rather than a uniform fix. Some answers recovered fully once the correct document was reliably retrieved. Others did not: one answer continued to state a specific figure that did not match the gold answer even with the correct source now present among the retrieved documents, and one continued to blend several genuinely unrelated figures from differently-purposed pages into a single confusing answer — on closer inspection, this second case likely was never a recency-driven crowding failure at all, but a same-keyword, different-context crowding pattern distinct from the one the recency fix targeted, or possibly reflects a genuinely ambiguous question against a corpus that states several different, period-specific values for the same nominal fact with no single canonical answer. The general point: a retrieval metric improving is necessary but not sufficient evidence that the generated answer improved, and the two need to be checked separately rather than assumed to move together.

### 5.3 Answer-discipline prompt rules, added in response to specific observed failures

A set of rules were added to the generation system prompt specifically in response to concrete failures observed during grading, rather than speculatively: an instruction to verify the retrieved source actually concerns the specific course, department, or applicant category the question names (the generation-layer counterpart to the URL-affinity retrieval fix in §2, added after repeatedly observing near-identical sibling pages for different departments being conflated); an instruction to preserve a stated approximation as an approximation rather than silently substitute a more precise-looking number pulled from an unrelated document; an instruction to give a single value rather than enumerate every retrieved candidate, and to state explicitly when sources genuinely disagree rather than silently choosing one or presenting several as equivalent; an instruction to prefer the most recent of several stated editions of a rule and name which year the answer applies to; and a cap on how many sources may be cited for a single factual claim.

### 5.4 A model instruction-following limit, and a fix that was tried and deliberately reverted

Even with the rules in §5.3 present, the locally-served, mid-sized open-weight model in use did not reliably follow the "single value" and "cap citations per claim" rules once several retrieved documents were simultaneously in context — specifically in cases where multiple documents genuinely discussed a similar or overlapping topic, the model would blend or dilute a correct, specific claim (including dropping a conditional exception the gold answer treated as essential) with tangential detail from lower-relevance sources, even when the single best, correctly-ranked source was present. This was diagnosed as a genuine capability limit under instruction load, not a missing instruction and not a retrieval failure, since the correct source being present and top-ranked was independently confirmed in the specific cases checked.

A targeted fix was drafted and briefly deployed: an explicit instruction telling the model that sources are presented in relevance order, to anchor its answer to the top-ranked source when it already gives a clear answer, and to draw on other sources only to fill a genuine gap the top source leaves open, restricted to sources clearly concerning the same specific subject. This was deliberately reverted the same day, before being kept, because its benefit is entirely conditional on an assumption — that the top-ranked source usually is the correct one — that this project's own retrieval history had repeatedly shown does not always hold (§4.3–§4.4's crowding regressions, and outright retrieval misses where no correct document was retrieved at all). Instructing the model to trust the top-ranked source more strongly helps exactly when that trust is warranted and actively worsens outcomes exactly when it is not, potentially turning a residual ranking error into a more confidently wrong answer rather than a hedged one, and risking under-use of genuinely necessary supplementary sources on questions that require synthesizing facts from more than one document. Properly validating the change would require regenerating and comparing answers across the entire evaluation set under the old and new prompt (temperature was fixed at zero, so this comparison would be exactly reproducible) rather than only checking the handful of cases the change was designed to fix — and that full check had not been done, so the change was held back pending it. It was noted as worth revisiting specifically once the underlying model is upgraded, since the instruction itself is generically reasonable guidance rather than a workaround narrowly tailored to the current model's specific weakness — though reintroducing it should still go through the same full before/after evaluation regardless of which model ends up in use.

## 6. Latency

Direct measurement of a realistic single chatbot turn — separating retrieval, translation and reranking from the upstream intent-classification call and the main answer-generation call — found that generation dominates total latency by roughly an order of magnitude over the entire retrieval pipeline combined, when served against the current locally-hosted, mid-sized open-weight model. This was attributed to the model-serving configuration rather than to any property of the retrieval pipeline itself, and retrieval-side latency was judged acceptable as measured. The practical conclusion was to defer further latency optimization until after a planned upgrade of the underlying LLM backend, rather than optimize a component that measurement showed was not the actual bottleneck.

## 7. Safety and abuse considerations

Prompt-injection defense (input isolation, described in §1) and an upstream in-scope/out-of-scope classification gate (a cheap, single-word classification call made before retrieval, deliberately fail-open so an infrastructure error does not block a legitimate user) were both implemented as part of the baseline system. A distinct, separate question — protecting the underlying corpus from systematic extraction via the chatbot interface — was considered but deliberately not built out beyond a basic recommendation, after distinguishing two different threat models that call for different levels of investment: protecting against compute-cost abuse or the effort invested in curating the corpus, versus protecting genuinely confidential information (which the corpus, being built entirely from the university's own already-public web pages, does not currently contain). For the former, lower-stakes threat model, request-rate limiting at the deployment layer plus a cheap prompt-level refusal of explicit bulk-extraction requests was judged proportionate; a more sophisticated query-pattern anomaly-detection system was judged not justified at this stakes level, but was explicitly flagged as a decision to revisit, not an assumption to carry forward unexamined, if non-public or confidential data is added to the corpus in the future.

## 8. Summary of what was tried and did not work, or was considered and not pursued

- **Semantic (embedding-boundary-aware) chunking for long documents**, as an alternative to fixed-size chunking — tested head-to-head across two evaluation rounds, found to make no measurable difference even on the specific long-document cases it targeted; fixed-size chunking (with header injection) kept for its simplicity.
- **A MaxSim-based late-interaction rescoring approach using BGE-M3's own multi-vector output** — scoped in technical detail, including the scoring formula and a concrete implementation sketch, but not built; superseded by a cross-encoder reranker that was implemented and validated instead, once it was judged good enough that the additional implementation risk of the MaxSim approach (particularly correct score normalization) was not worth incurring for a second, unvalidated mechanism.
- **A full first-stage, token-level multi-vector retrieval architecture (the ColBERTv2/PLAID design)** — investigated in depth, explicitly not built, on the combined grounds that it solves a corpus-scale problem this project does not have and that diagnostic evidence showed the project's actual failures were ranking-order problems, not recall-ceiling problems.
- **Hybrid sparse/lexical retrieval** — scoped in detail as a promising complementary mechanism for exact-match queries, not implemented, sequenced behind other work.
- **Lowering the recency-scoring weight back toward zero**, as a candidate fix for the freshness-scoring regression in §4.4 — considered and rejected in favor of the more surgical fix of correcting what an unresolvable year defaults to, since reducing the weight globally would have reopened the crowding problems the weight had just been reintroduced to help solve.
- **An explicit "anchor to the top-ranked source" generation instruction** — implemented, then reverted the same day, for the reasons in §5.4: it trades a benefit conditional on ranking quality for a risk that materializes precisely when ranking quality is imperfect, which this project's own retrieval history gave good reason to expect would actually occur.
- **A subset evaluation index containing only target documents** — rejected, since it would remove the very distractor documents that create the failure modes under study, making the evaluation unrepresentative of production conditions.
- **Sophisticated anomaly-detection-based anti-scraping infrastructure** — considered and judged disproportionate to the actual threat model at this stage; a simple rate limit plus a prompt-level refusal of explicit bulk-dump requests was judged sufficient for now.

## 9. Open problems and known limitations

- A confident, fluent, correctly-formatted, and *specifically wrong* answer (naming a real but incorrect person, phone number, or figure with full apparent confidence) remains the most concerning failure mode observed, precisely because nothing about its presentation signals a reader that it might be wrong.
- At least one case was found where the underlying university documentation appears to genuinely contradict itself across two of its own published pages — a finding about the source data's own quality, not something any retrieval or generation mechanism can be expected to resolve on its own.
- The model's inconsistent adherence to its own explicit answer-discipline instructions when several retrieved documents are present in context (§5.4) remains open, with a prompt-level fix considered, deliberately not deployed, and queued for reconsideration after a planned model upgrade.
- Obfuscated contact information appearing in the source corpus in a deliberately mangled form (to deter scraping of the original pages) was found to leak through into generated answers in its unusable, obfuscated form rather than being normalized at ingestion — a data-cleaning gap rather than a retrieval or generation defect.
- Only a single chunk per source document reaches the generation step in the current architecture; a question requiring two separate facts located in different parts of one long document is, by construction, not answerable even if that document is perfectly retrieved. Supporting multiple chunks per document, with chunk-level rather than only document-level reranking, was identified as a needed architectural extension and not yet implemented.
- Evaluation results files do not yet record the full retrieval configuration (which mechanisms were active and at what settings) that produced them, which has repeatedly forced reconstructing a run's actual configuration from indirect evidence after the fact — a fix was identified (record every relevant flag and weight in the results file itself) but had not been implemented as of this writing.
- The specifics of the corpus/index rebuild described in §3 (what changed between the earlier and later corpus versions) were not captured in project documentation at the time, and could not be reconstructed for these notes.
